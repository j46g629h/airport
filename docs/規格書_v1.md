## 1. 系統目的與範圍

### 要解決的問題

PCI adidas 工廠的台幹出差與休假，機場接送安排目前記錄在一份 Excel（`airport.xls`），
每週一個分頁，用 WhatsApp 或口頭傳達。問題是：

- 員工要知道自己幾點的車，只能打電話問
- 管理者要回答同一個問題很多次
- 資料只有一份、在一個人手上

### 系統要做到

| # | 目標 |
|---|---|
| 1 | 使用者自己上網查得到接送資訊，不用問人 |
| 2 | 使用者能知道同一天／同班機還有誰（可以一起搭車） |
| 3 | 使用者能對自己那筆提出額外需求 |
| 4 | 管理者能用 app **或直接編輯 Google Sheet** 輸入資料（兩個入口都要能用） |
| 5 | 管理者在手機上就能操作 |
| 6 | 超級管理者每天收到本週動態與異常提醒 |

### 不在範圍內

- 司機、保衛、接待**不使用**這個系統
- 不做員工線上申請與簽核（那要跟出差流程整合，是另一個題目）
- 不寄信給使用者（系統信只給管理者與超管）
- 第一版不做 QR Code 海報

### 規模

| 項目 | 數字 |
|---|---|
| 每週接送 | 約 10～25 筆 |
| 一年 | 約 250～400 筆 |
| 使用者 | 台幹及眷屬，來源資料裡有 52 位 |
| 管理者 | 超級管理者 2 位 ＋ 一般管理者 1～2 位 |
| 人員名冊 | 初版 52 筆，預計擴充到 100 筆 |
| 航班名冊 | 初版 25 筆，預計擴充到 60 筆 |

Google Sheet 單檔上限 1000 萬格，以 26 欄計可存 38 萬筆——**容量完全不是限制**。
真正的限制是 Apps Script 每次回應 3～8 秒。

## 2. 角色與權限

| 功能 | 使用者 | 管理者 | 超級管理者 |
|---|:---:|:---:|:---:|
| 用 email 查自己的行程 | ✅ | ✅ | ✅ |
| 用日期／航班號查同班機名單 | ✅ | ✅ | ✅ |
| 對自己那筆提出需求 | ✅ | — | — |
| 查詢全部資料（不限 3 個月） | ❌ | ✅ | ✅ |
| 新增／修改／取消接送 | ❌ | ✅ | ✅ |
| 批次改期 | ❌ | ✅ | ✅ |
| 人員名冊、航班名冊維護 | ❌ | ✅ | ✅ |
| 動態表（統計） | ❌ | ✅ | ✅ |
| 帳號管理 | ❌ | ❌ | ✅ |
| 發送報表 | ❌ | ❌ | ✅ |
| 接收每日系統信 | ❌ | ❌ | ✅ |

### 認證方式

| 角色 | 認證 |
|---|---|
| 使用者 | 輸入 email 即可，**沒有密碼** |
| 管理者 / 超管 | 帳號 ＋ 密碼（加鹽 SHA-256 迭代 1000 次，token 存 `sessionStorage`，效期 6 小時） |

### 超級管理者為什麼是 2 位

只有 1 位的話會有一個沒有出口的死角：**他忘記密碼時沒有任何人能幫他重設**，
因為重設密碼是超管專屬功能，而他就是唯一的超管。休假、離職也一樣沒有人接手。

（「不小心把自己停用」不會發生——`guardLastActiveSuper()` 會擋掉「停用最後一位啟用中的 SUPER」。）

## 3. 使用流程

### 3.1 使用者查詢

```
開網址
 ├─ 輸入 email        → 我的行程（含眷屬，因為共用同一個 email）
 └─ 輸入日期 或 航班號 → 同日／同班機名單
```

**兩種查詢都不需要驗證身分，且顯示完整資訊、不遮蔽個資。**

> 這是刻意的決定。使用者的實際需求是「知道當天同班機有誰，能不能一起搭車」，
> 遮蔽姓名以外的欄位會讓這個需求無法滿足。
> 補強措施：所有頁面加 `noindex`，讓 Google 搜尋不到；網址靠內部傳遞。

**時間範圍限制：**

| 對象 | 看得到 |
|---|---|
| 使用者 | 航班日期在「今天往前推 3 個月」之後的全部（含已取消、已改期、已完成）。未來的不設限 |
| 管理者 / 超管 | 全部，沒有時間限制 |

**特殊狀態的顯示：**

| STATUS | 使用者看到 |
|---|---|
| 已改期 | 新日期 ＋「已改期（原訂 15/09/2026）」 |
| **待定** | **「日期待定，請洽管理者」**，不顯示原本的日期（否則他會照舊日期去等車） |
| 已取消 | 「已取消」 |

### 3.2 使用者提出需求

```
在「我的行程」上點某一筆 → 填寫需求 → 送出
   ↓
寫進主表 T 欄 PERMINTAAN 員工需求
   ↓
立刻寄信通知管理者（不等每日系統信，那可能來不及）
```

四條規則：

| 規則 | 說明 |
|---|---|
| 只能改自己那筆 | 後端會再驗證一次 email，不能只靠前端擋 |
| 出發前 **12 小時**鎖定 | 車已排好，前一小時才說「我多兩件行李」沒有人看得到 |
| 送出後立刻寄信給管理者 | — |
| 記錄提交時間 | 管理者才知道是什麼時候提的 |

⚠️ **`PERMINTAAN 員工需求`（T 欄）與 `REMARK 備註`（Q 欄）是兩個獨立欄位。**
Q 欄只有管理者能填。管理者在 app 上同時看到兩欄，可以按一鍵把需求併進 REMARK，也可以不理它。
使用者永遠改不到 Q 欄——來源資料裡的 `Tamu EDC, Schedule PGS Antar ke Bandara`、`A 1020 FM`
是作業指示，被覆蓋掉會出事。

### 3.3 管理者新增一筆

```
打 email（或中文名／英文名）
   ↓
找到 1 位 → 直接帶入
找到多位 → 跳選單挑人 → 帶入
   ↓
自動填好：NAME、中文姓名、DEPT、FACTORY、DORM、HP
   ↓
打航班號 → 自動帶入 ETD/ETA（輸入即篩選，打 CI 就跳出 CI761/762/764）
   ↓
選出廠時間（日期時間選擇器；送機遇凌晨航班時預選前一天，可改）
   ↓
送出 → 寫進對應的週分頁 → 更新 _INDEX
```

### 3.4 管理者查詢與修改

**篩選條件（可組合）：** 日期區間、接／送、廠別、部門、姓名或 email 關鍵字、航班號、狀態、
**有未處理的員工需求**（這個最實用，一眼看到誰提了需求還沒處理）。

**排序：** 日期、姓名、航班號、最後更新時間。

**修改：**

| 動作 | 處理 |
|---|---|
| 改欄位 | 寫回週分頁，記錄 X/Y 欄（最後更新時間、更新者） |
| 改日期跨到別週 | 從舊週分頁**搬到**新週分頁。app 上改會自動搬；手動改的話每日重建會修正 |
| 改期 | STATUS 設「已改期」，W 欄自動填入原訂日期 |
| 日期未定 | STATUS 設「待定」，**A 欄日期保留不動** |
| 取消 | STATUS 設「已取消」，**不刪列** |

**批次改期：** 航班延誤或取消時，同一班機通常是一整車人一起受影響
（來源資料裡 `CI761` 一次最多 3 人、`CZ388` 3 人）。
篩選 → 全選 → 一次改時間。比一筆一筆改快，而且不會漏掉人。

## 5. 關鍵設計決策與理由

### 5.1 為什麼用 Google Sheet 當資料庫，不用 Firebase / MySQL

**因為「管理者要能直接在 Google Sheet 輸入」這條需求。**

如果資料放在真正的資料庫，而管理者又要能在 Sheet 打字，就必須做**雙向同步**：
Sheet 改了推去資料庫、資料庫改了推回 Sheet。雙向同步是軟體工程裡最容易壞的東西之一——
兩邊同時改同一筆誰贏？網路斷在中間怎麼補？這會變成整個專案最大的 bug 來源，
而且是「平常都對、偶爾錯一筆、錯了沒人發現」那種。

**用 Google Sheet 當資料庫，這個問題直接消失，因為只有一份資料。**

### 5.2 為什麼保留每週一個分頁，又不會拖慢程式

使用者要求 Sheet 格式與 `airport.xls` 一致（每週一個分頁）。
純用週分頁的問題是「查一個人整年的紀錄要掃 52 張分頁」，光讀就要 3～10 秒。

**解法：週分頁是真實資料，另外維護一張 `_INDEX` 攤平表，單向衍生。**

這跟 5.1 反對的雙向同步是**完全不同的東西**：`_INDEX` 永遠不能被改，它是算出來的。
壞了重算就好，不會掉資料，也沒有「誰贏」的問題。就像 Excel 的公式——
算錯了不會弄壞原始資料。

### 5.3 為什麼 `ETD/ETA` 一欄就夠

驗證過 89 筆資料的 25 個航班號：**每一個航班號都只出現在接機或只出現在送機，沒有一個兩邊都有。**

| 接機（ETA） | 送機（ETD） |
|---|---|
| CI761 → 13:35 | CI762 → 14:40 |
| BR237 → 13:20 | BR238 → 14:30 |
| CX719 → 19:40 | CX718 → 08:10 |
| CZ8353 → 23:00 | CZ8354 → 00:20 |
| VN631 → 13:00 | VN630 → 13:50 |
| CX797 → 23:00 | CX798 → 00:05 |
| CA475 → 21:30 | CA476 → 23:00 |

航班號本身（奇數進、偶數出）已經決定了它是抵達還是起飛時間，
程式從 B 欄的接／送就能判斷，不需要拆成兩欄。

### 5.4 為什麼主表不放 `person_id`

主表存的是快照。如果改用 `person_id` 關聯名冊，刪掉名冊的一列就會讓歷史紀錄變成孤兒。
存快照則是：**名冊怎麼改、怎麼停用、甚至直接在 Sheet 上刪列，歷史紀錄一筆都不會壞。**

副作用是「打錯字要修正時舊紀錄不會跟著改」——用「改名冊時跳提示讓使用者選」解決。

### 5.5 Google Sheet 為什麼雙語而不是純印尼文

Sheet 上工作的人（管理者、超管）兩種語言的人都有。而且雙語成本趨近於零：
只有 **B 欄（接／送）和 S 欄（狀態）** 兩個欄位有固定選項需要翻譯，
其他都是姓名、航班號、時間這種沒有語言問題的資料。

表頭方面，`airport.xls` 現有的 17 個標題裡，7 個已經是雙語、9 個是印尼文與英文相通的詞
（`DATE`、`DEPT`、`NAME`、`FLIGHT`、`DORM`、`REMARK`…），**只有 `上車地點` 是純中文**，
補成 `上車地點 TITIK JEMPUT` 即可。**整份表頭只改 1 格。**

⚠️ 這一點刻意違反 KANTIN 設計約定第 1 條（Sheet 存代碼不存顯示文字）。
破例的理由是這個專案「人要直接看 Sheet、直接改 Sheet」是硬需求，可讀性變成必要條件。
代價用**下拉選單只允許固定值** ＋ 程式讀進來立刻映射成代碼（映射表只寫在 `Config.js` 一處）控制住。

## 6. 格式規範

| 項目 | 規範 | 說明 |
|---|---|---|
| 日期 | `dd/mm/yyyy` | 西元年，不用民國年 |
| 時間 | 24 小時制 `HH:mm` | |
| 日期時間 | `dd/mm/yyyy HH:mm` | |
| 出廠時間（Sheet 上） | `20:00` 或 `30/08 20:00` | 純文字欄，見 `CLAUDE.md` 設計約定第 3 條 |
| 星期 | **不顯示** | 使用者明確表示不需要 |
| 時區 | `Asia/Jakarta`（GMT+7） | **三個地方都要設**，見 `CLAUDE.md` 常見陷阱 |

**app 上的日期時間輸入一律用 `<input type="datetime-local">`**（原生，零成本，手機上跳系統轉盤）。

⚠️ 它的顯示順序跟著手機系統地區設定走，HTML 和 CSS 都改不了。
**解法：輸入框下方即時顯示一行 `28/08/2026 20:00` 確認文字**，那一行由我們控制。

## 7. 通知與報表

### 7.1 每日系統信（只寄給超級管理者，收件人可設多個）

| 順序 | 段落 | 內容 |
|---|---|---|
| ① | **待定中的行程** | STATUS = 待定 的全部，顯示「已待定 N 天」，超過 3 天標紅（天數可在 `PENGATURAN` 改） |
| ② | 今日與明日出車 | 從本週裡挑最近兩天。**用出廠時間篩選，不是航班日期**（跨午夜航班的車前一天就出發） |
| ③ | 本週動態 | 本週（週一～週日）全部行程，接／送分開列 |
| ④ | 資料異常健檢 | 缺日期、出廠時間格式看不懂、email 在名冊查無此人、航班號不在航班名冊、超過 N 天沒更新 |
| ⑤ | 昨日新增的員工需求 | 幾筆、誰提的、內容 |
| ⑥ | 系統錯誤 | 有才出現 |

**第 ④ 段是「兩個輸入口」這個設計的安全網。** 手動在 Sheet 打字一定會有錯，
重點不是防止，是讓錯誤在害到人之前被看到。

|---|---|
| 使用者提出需求 | 管理者 ＋ 超管（立刻） |

| **Excel 日月顛倒誤判** | `Mr Matt Ho` 04/09 那筆出廠時間被讀成 `09/03/2026` → `03/09/2026 20:00` |
| **Excel 日月顛倒誤判** | `Ms Joeling Hsiao` 04/09 那筆 → `03/09/2026 21:00` |
| 航班號空格 | `Mr Xia Xu Yi` 的 `"CZ 8056"` → `"CZ8056"` |

> 中間那兩筆**在原始 Excel 裡就是錯的**——有人想寫 9 月 3 日，打了 `03/09 20:00`，
> Excel 照 mm/dd 讀成 3 月 9 日，於是 9 月的分頁裡躺著兩筆 3 月的資料。
> **這正是「出廠時間欄必須設成純文字」的理由。**

## 10. 已知限制與未來可加的功能

### 已知限制

| 限制 | 說明 |
|---|---|
| Apps Script 每次回應 3～8 秒 | 這是 Google 那端的執行時間，改不掉。優化方向是「讓使用者不必等」（快取 ＋ 背景更新），不是「讓它變快」 |
| `/exec` 網址偶發 404 | 實測約 7%，前端必須自動重試一次（KANTIN 設計約定第 19 條） |
| GitHub Pages 網站是公開的 | Pro 只保護原始碼，不保護網站。要讓網站也需登入需要 Enterprise Cloud |
| `datetime-local` 顯示順序管不了 | 跟著手機系統走。用下方的確認文字補足 |
